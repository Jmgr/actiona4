# Agent instructions

## Workspace layout

Cargo workspace, edition 2024. Crate names below are directories under `crates/`; where the
library name differs it is given in parentheses.

| Crate | Purpose |
| --- | --- |
| `types` | Leaf primitives: `Point`, `Rect`, `Size`, `Color`, display and platform types, with optional `opencv` / `imageproc` conversion features. Depended on by nearly everything. |
| `common` (`actiona_common`) | Bits shared between the main binary and the extension binaries: crash reporting (Sentry + minidump), selection helpers, build info via `built`. |
| `config` | On-disk settings and persistent state (TOML under the platform config dirs). |
| `core` (`actiona_core`) | The scripting API surface. `src/api/` holds one module per JS/TS namespace (`mouse`, `keyboard`, `image`, `file`, `windows`, `clipboard`, …) exposed through `rquickjs`. The largest crate; most feature work lands here. |
| `macros` | Proc macros used by `core` and `action-definition`: `#[js_methods]`, class/enum derives, `from_js_object`, platform gates, action definitions. |
| `action-definition` | Declarative catalogue of actions (parameters, schemas, Fluent i18n, RPC types), grouped under `src/actions/` as `clipboard`, `flow`, `misc`, `mouse`, `random`, `system`, `window`. |
| `action-execution` | Runtime that executes action trees, on top of `action-definition` + `core`. |
| `file-format` | Script document storage: SQLite database (`rusqlite` + migrations) and chunked attachments. |
| `screenshot` | Low-level cross-platform screen capture (`Capture`, `Screen`, pixel-format helpers). |
| `extension` | IPC framework for out-of-process extensions: `Host` and `Extension` sides, plus the wire protocols. |
| `extensions/selection` | Extension binary `extension-selection`: on-screen region selection overlay (`winit` + `pixels`). |
| `run` | Entry point. Builds `actiona-run` (CLI) and, on Windows, `actiona-runw` (GUI subsystem). Wires together `core`, `config`, `updater`, `installer-tools`. |
| `updater` | Update checks and downloads against release channels. |
| `installer-tools` | Install/update helpers shared by `run`, `inno-plugin` and `xtask`: packaging, PATH, settings, Windows notifications. |
| `inno-plugin` | Windows-only DLL loaded by the Inno Setup installer; a thin FFI shell over `installer-tools`. |
| `build-support` | `build.rs` helpers, currently Windows manifest embedding. |
| `doc-generator` | Binary that reads rustdoc JSON for `actiona_core` and emits the TypeScript API declarations. |
| `e2e` | End-to-end harness: Rust test driver (`tests/e2e.rs`, `tests/manual.rs`) running the TypeScript scripts in `crates/e2e/scripts/` through a built `actiona-run`. |
| `xtask` | Build automation binary: documentation generation, `lint-ts`, AppImage / installer / archive packaging, symbol upload. |

TypeScript declaration files:

- `crates/run/assets/index.d.ts` — generated by `cargo make doc` (`xtask doc`, via
  `doc-generator`). Never edit by hand; change the Rust doc comments in `core` and regenerate.
- `crates/e2e/scripts/globals.d.ts` — hand-written test helper declarations. Edit freely.

## Common tasks

- `cargo make test` — unit and integration tests.
- `cargo make e2e` — builds `actiona-run`, then runs the TypeScript end-to-end tests.
- `cargo make doc` — regenerates the TypeScript declarations (Linux only).

## CI

CI is GitHub Actions: <https://github.com/Jmgr/actiona4/actions>. Use the `gh` CLI rather
than fetching that page — the web UI is client-rendered and returns nothing useful.

- `gh run list --limit 5` — recent runs and their status.
- `gh run view <id>` — job breakdown for a run; `--log-failed` for the failing step's output.
- `gh run watch <id>` — follow an in-progress run.

`.github/workflows/build.yml` (`CI`, on push and pull request) runs `format`, `linux-lint`,
`windows-lint`, `doc`, `linux-test`, `windows-test`, `linux-e2e`, `windows-e2e`, `appimage`
and `windows-archive`. `release.yml` handles releases.

Not everything CI checks can be reproduced locally: the Windows jobs, and Linux jobs whose
system dependencies differ from a local machine's, can fail on a change that is clean here.
When a change touches platform-specific code, check the run rather than assuming.

Only read CI state. Do not re-run, cancel, or dispatch workflows without being asked.

## Formatting and linting

- After every change, run `cargo make format` and `cargo make lint`.
- Do not run `cargo fmt` or `cargo clippy` directly — the `cargo make` tasks wrap them with
  the required toolchain, flags and extra steps (`derivefmt`, `sort`, TypeScript linting).

## Git

- Never commit changes. Leave the working tree for the user to review and commit.
- Never unstage what is already staged. If you need to stash, use
  `git stash push --index` and `git stash pop --index` so the index is preserved.

## Filesystem access

- Stay inside the project directory. The only exception is the cargo crate cache
  (`~/.cargo/registry`, `~/.cargo/git`), which may be read when inspecting dependencies.
- Never run `find /` or any equivalent whole-filesystem search (including the Windows
  equivalents such as `dir /s C:\` or `Get-ChildItem -Recurse C:\`).
